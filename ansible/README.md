# Set up the Hoard server

This playbook hardens the bastion and the private app VM from `terraform/`, installs Docker on the app VM, and starts Hoard. The app VM has no public IP: Ansible reaches it through the bastion.

The `common` role runs on both VMs. It updates packages, opens only the ports in `common_open_ports` (22 and 80 on the app VM, 22 alone on the bastion), turns off root and password login, and installs fail2ban plus automatic security upgrades.

The `docker` role installs Docker Engine and the Compose plugin from Docker's apt repository, rotates container logs (5 files of 10 MB each per container), and adds the admin user to the `docker` group.

The `app` role logs in to the Azure Container Registry with a short-lived token from the controller's `az login`, writes a production Compose file, applies database migrations and seeds the categories and admin account with the `hoard-migrate` image, then starts Hoard. The API and the web app connect to the Azure PostgreSQL server over TLS (`sslmode=require`); its host and password come from the Terraform outputs. The image tag defaults to `main`; CD passes the commit SHA. The load balancer sends port 80 to the web container.

The deploy steps run in a `block` with a `rescue`. If migrating, starting or the health check fails, the play prints `docker compose ps` and the last 40 log lines of every container, then stops with the failing step's name. A failed image pull also says to check the tag was pushed and that the `az` identity can pull from the registry.

## Prerequisites

- Terraform has been applied in `terraform/`, so the bastion, app VM, database and registry outputs exist
- The Azure CLI, signed in (`az login`) as someone with `AcrPull` or `AcrPush` on the registry. The subscription owner already has it.
- The SSH private key `~/.ssh/hoard` (the pair created for Terraform)
- Ansible, including the `community.general` collection, which the Ubuntu `ansible` package provides

```bash
sudo apt install ansible
```

## Secrets

Copy the example and replace the JWT secret and the admin password. The JWT secret must be at least 32 characters. The database password is generated by Terraform and read from its outputs, so it is not in the vault.

```bash
cp group_vars/hoard/vault.yml.example group_vars/hoard/vault.yml
ansible-vault encrypt group_vars/hoard/vault.yml
```

`vault.yml` is not committed. CD writes its own copy from the `production` environment secrets.

## Inventory

The inventory is dynamic. `ansible.cfg` points at `inventory/terraform.py`, which Ansible runs every time. It reads `terraform output -json` from `../terraform` and returns the bastion in the `bastion` group and the app VM's private IP in the `hoard` group, with `admin_username` as the SSH user and the private key from `ssh_command`. Hosts in `hoard` connect through a `ProxyCommand` that hops via the bastion, and also get the database, registry and app URL outputs as variables. A new host key is accepted on first contact; a changed one is refused, so after recreating a VM run `ssh-keygen -R <ip>`. There is no file to generate or keep in sync: after `terraform apply` the playbook finds the new VM, and after `terraform destroy` the inventory is empty.

Check what Ansible sees:

```bash
cd ansible
ansible-inventory --graph --ask-vault-pass
```

Set `HOARD_TERRAFORM_DIR` to read the outputs of a different Terraform directory, and `HOARD_SSH_KEY` to use a private key at another path (CD uses this).

## Run the playbook

From the `ansible` directory:

```bash
cd ansible
ansible-playbook playbook.yml --ask-vault-pass
```

Run it a second time. When the server is already in the desired state, the recap shows `changed=0`.

**Pin the image tag on manual runs.** CD always deploys with `-e image_tag=<commit sha>`. Without it, the playbook uses `main`, and because images are pulled only when missing, a VM that already has an older `main` image keeps running it. To deploy or re-apply by hand, pass the SHA that is live (the latest **Deploy to Production** run shows it):

```bash
ansible-playbook playbook.yml --ask-vault-pass -e image_tag=<commit sha>
```

`ansible.cfg` turns on SSH pipelining, so each task needs one round trip through the bastion instead of several. A run with nothing to change takes about 80 seconds instead of 160.

## Check the result

On the app VM (`terraform output -raw ssh_command` opens a shell through the bastion):

```bash
sudo ufw status
sudo sshd -T | grep -E 'permitrootlogin|passwordauthentication|maxauthtries|x11forwarding'
systemctl is-active fail2ban
sudo docker compose --env-file /opt/hoard/hoard.env -f /opt/hoard/docker-compose.prod.yml ps
```

`ufw status` lists 22 and 80 (22 alone on the bastion). `permitrootlogin`, `passwordauthentication` and `x11forwarding` are `no`, and `maxauthtries` is `3`. fail2ban is `active`. The Compose listing shows `api` and `web` running and healthy. Open `terraform output -raw app_url` in a browser.
